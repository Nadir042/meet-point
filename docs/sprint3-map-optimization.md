# Sprint 3 地图推荐优化

实现分支：`feat/cyy-sprint3-map-optimization`；基线提交：`1a75dfb`。

## 速度与缓存

- 多关键词搜索最多同时处理 3 个关键词，结果仍按关键词原始顺序合并、去重。
- 保留原来的接口级限流、超时和重试；生产默认 `AMAP_QPS=2`，没有为提速提高配额。
- 每个高德 provider 实例独立缓存：地点搜索 60 秒、成功的路线结果 30 秒；总容量最多 256 项，按最近访问淘汰，访问时清理过期项。
- 缓存键包含实际接口路径及请求参数。地点关键词、中心、城市，以及路线端点、城市、交通方式变化时会使用不同条目。
- 不缓存失败结果。缓存只存地图返回的地点/路线信息，不存活动、账号、成员 ID、选票或最终推荐结果。读取时复制数据，防止相互修改。
- 不共享尚未完成的跨请求任务，防止某一活动取消或超时影响另一活动。一次推荐内原有的相同路线复用仍保留。
- 改预算后可复用地点及路线数据，但重新筛选、评分、生成新轮候选；缓存不会绕过权限和推荐期间的活动版本检查。
- 缓存不落盘，重启清空。不能保证冷启动、多成员多方式场景都在 10 秒内完成，仍取决于接口限流、网络、候选数量和实际路线数量。

## 预算规则

用户确认的口径：**每人的地点人均消费预算，不含交通费**。

1. 页面填写“下限－上限”两个数字，新成员初始为空；前后端均要求 `0 ≤ budgetMin ≤ budgetMax ≤ 5000`，支持小数，拒绝空值、非数字、负数和上下限倒置。
2. 老数据和老客户端的单值 `budget` 按 `0—budget` 读取；保存新区间后保留 `budget=budgetMax` 作为兼容字段。
3. 从高德 `biz_ext.cost` 提取参考人均消费，仅接受有效且非负的数字/数字字符串。`0` 是有效值；空值、空数组、空格、负数或非数字视为未知，不推断为免费。
4. 使用所有成员区间的交集：共同下限取最大值，共同上限取最小值。例如 `80—150` 与 `100—120` 的共同范围是 `100—120`。低于共同下限或高于共同上限的已知消费地点，在调用路线接口前排除，边界值保留。
5. 区间没有交集时，在调用地图前返回 `BUDGET_CONFLICT` 并提示协商调整。所有地点因已知消费不符合区间被排除时返回 `NO_CANDIDATES`，不自动放宽范围；审批失败保留原轮次、截止时间、选票与待处理申请。
6. 在候选池补位、综合排名和三组 Top3 排序中，优先选择已确认位于全部成员预算区间内的地点，同级再按原距离或评分规则排序。不同偏好的候选预留机制仍保留。
7. 价格未知的地点作为备选，显示“未知，需核实预算”，不保证其实际消费符合区间，不伪造价格或视为免费。历史输入未提供预算时不制造限制，也不声称已确认符合全部成员预算。
8. 原四维评分计算不变，预算决定候选资格和排序优先级。路线 `cost` 仍只表示交通费用，未混用。

高德消费值是参考信息，不保证商家的实际消费。缺失数据保留为未知。

依据：[高德搜索 POI 文档](https://lbs.amap.com/api/webservice/guide/api-advanced/search)，`extensions=all` 下的 `biz_ext.cost` 为人均消费，仅部分 POI 类别提供。

## 偏好与地点

- 继续先按活动类型过滤；保留对交通设施、停车场及住宅等类别的排除。
- 完善影城、购物中心、桌面游戏、陶艺、DIY、拼豆、摄影等别名/检索词。
- 线下会面已存在的“逛街”选项允许匹配商场/购物中心，解决选项可选但类别被排除的问题。
- 所有人都有具体偏好且存在匹配时，只将匹配至少一项偏好的预算可用地点纳入路线查询。
- 有成员选择“不限”时，保留活动类型内更广的候选，具体偏好继续影响排序。
- 在最多 10 个路线候选中，先为不同偏好保留匹配地点，优先选择预算已确认符合者、同级取最近地点，再按相同顺序补齐。最终三组 Top3 先按预算确认状态、再按原评分排序。
- 无匹配时保留同活动类型备选并明确警告；原有无地点时的活动类型搜索回退继续保留。
- 自定义输入用于提取想去的场所词，例如“安静的书店”搜索“书店”。关键词与预设偏好一同查询，沿用相同的并发、缓存、排序和备选规则。表单和接口拒绝“不要咖啡厅”等排除条件。
- 明确选择相关自定义场所时，线下会面额外接纳书店，休闲娱乐额外接纳博物馆、美术馆和展览馆。这些地点需要匹配高德返回的类别，聚餐继续使用餐饮类别，交通设施、停车场和住宅仍排除。

## 接口与页面兼容

候选增加可选字段，旧字段及三组结构保持：

| 字段 | 含义 |
|---|---|
| `venueCost` | 地点参考人均消费，未知为 `null` |
| `venueCostStatus` | `known` / `unknown` |
| `venueCostSource` | 高德数据可用时为 `amap.biz_ext.cost`，否则为 `null` |
| `budgetStatus` | `within`：已知消费位于各成员预算区间内；`unknown`：消费未知；`unverified`：成员预算信息不全 |

需求接口新增 `budgetMin` / `budgetMax`，必须成对提交，旧 `budget` 输入继续兼容。预算和偏好说明加入现有 `reasons` / `warnings`。页面仅调整预算输入、成员预算区间和卡片参考消费说明，沿用原有配色、卡片和弹窗布局；投票、权限及图片未改动。

## 性能复现

脚本仅使用内存模拟地图 HTTP 响应，无须 Key：

```bash
node scripts/benchmark-map.js
```

需要与旧地图模块对照时，可创建独立基线工作区：

```bash
git worktree add --detach ../meet-point-baseline 1a75dfb
node scripts/benchmark-map.js ../meet-point-baseline/amap.js
```

每场景重复 3 次，报告中位耗时和请求数。模拟每次 HTTP 延迟 120ms，测试用 QPS=20、3 个候选；只隔离比较地图 provider 的调度和缓存，两个版本使用同一推荐逻辑。这个 QPS 是实验参数，不是线上配置建议。缓存内的即时重复推荐可减少外部请求；超过有效期或缓存容量后需重新请求。

2026-11-25 本地模拟结果（毫秒；每个请求数在 3 次重复中一致）：

| 场景 | 优化前首次 / 重复 | 优化后首次 / 重复 | 首次请求数：前 → 后 | 重复请求数：前 → 后 |
|---|---:|---:|---:|---:|
| 2 人，步行 | 1199 / 1197 | 947 / 1 | 9 → 9 | 9 → 0 |
| 4 人，步行＋公交 | 1720 / 1726 | 1474 / 1 | 27 → 27 | 27 → 0 |
| 9 人，四种交通方式 | 5067 / 5069 | 4807 / 2 | 111 → 111 | 111 → 0 |

首次请求数量不变时，改善来自搜索阶段重叠等待；预算和偏好过滤还能在有不合适候选时减少后续路线请求，该收益不包含在此表中。缓存命中的 1—2ms 仅为进程内模拟测量，不代表浏览器端响应时间或真实线上承诺。
