# MeetPoint 响应式前端改造设计

日期：2026-11-13  
分支：`zqz/frontend`  
基线：PR #15 的高德地点搜索、路线与推荐能力

## 1. 目标

在不重写现有原生 HTML、CSS、JavaScript 架构的前提下，把 MeetPoint 改造成简洁、美观、大气、可在手机和电脑完整使用的响应式 H5 产品。

本轮以 `PRODUCT.md`、正式 SRS、最终版用户故事和 `265.pptx` 为事实来源；视觉规则以 `DESIGN.md` 为准。

成功标准：

1. 用户可以在手机和电脑完成“创建或加入活动 → 填写需求 → 查看三类推荐 → 投票或改票 → 查看结果 → 打开导航”的同一流程。
2. 页面呈现“城市会面手册”风格：米白背景、暖黑文字、珊瑚橙主行动、轻卡片和柔和圆角。
3. 手机正文保持可读，核心触控目标至少 44px，不再通过 8–10px 小字压缩内容。
4. 推荐理由、未知费用、隐私状态和错误原因如实展示。
5. 现有业务测试不因纯视觉调整新增失败；新增或调整的交互具备针对性测试。

## 2. 范围

### 本轮包含

- 统一全局颜色、字体、间距、圆角、阴影、焦点和按钮层级。
- 重整顶部导航、页面标题、活动概览、成员需求、推荐地图、候选地点、投票、结果和弹窗。
- 针对桌面宽屏、常规笔记本、约 390px 手机和约 360px 窄屏设计明确布局。
- 让前端保存出行需求遵循 Apifox/OpenAPI 的 `PUT /requirements` 契约。
- 在契约可用时接入 `/locations/reverse`，用于用户明确授权后的当前位置解析。
- 为超时、配额不足、路线不可用、无结果和一般网络失败提供不同提示与恢复动作。
- 在高德前端地图配置可用时显示真实交互地图；未配置时明确说明，不用示意图冒充真实地图。

### 暂不包含

- 重写为 React、Vue 或其他框架。
- 修改推荐算法、数据库结构或后端部署方案。
- 在 C 的投票历史接口尚未完成时伪造历史数据；只保留可接入的清晰边界。
- 自建应用内语音导航；最终结果继续跳转高德地图。
- 将 PPT 的展示页逐像素复制为产品页面。

## 3. 用户故事对应流程

### 3.1 创建与加入

- 发起者创建活动，填写名称、日期、时间、活动类型和昵称。
- 一般成员通过邀请链接或 6 位邀请码加入。
- 页面明确显示当前身份、活动状态和下一步，不把示例数据误认为线上共享数据。

### 3.2 填写个人需求

- 用户搜索出发地，或在明确授权后使用当前位置。
- 用户选择交通方式、活动偏好和预算，并决定是否向其他成员公开具体出发地。
- 保存操作使用 `PUT /requirements`；成功后返回活动流程并显示已完成状态。
- 未公开地点仍可参与推荐计算，但其他成员视角只能看到隐私化状态。

### 3.3 查看推荐

- 推荐按“最公平、最合口味、最方便”分组，每组最多展示 3 个候选点。
- 默认优先展示最公平组，同时让其他组在手机上可轻松切换。
- 每个候选点优先显示地点名、排名、平均时间、公平度、费用状态和简短推荐理由。
- 进一步解释通过展开区或地图详情呈现，避免首屏信息过载。

### 3.4 投票与结果

- 成员可以投票和改票，并看到自己的选择、当前进度和截止状态。
- 发起者在满足规则后确认结果；平票、零票和重新推荐状态需要明确说明。
- 最终结果展示地点、核心路线信息和“打开高德导航”主操作。
- 投票历史等 C 的接口完成后再接入，不能用本地假数据代替线上记录。

## 4. 视觉与交互结构

### 4.1 页面外壳

- 桌面：顶部品牌、主要导航、身份入口保持在一行；内容使用居中宽容器。
- 手机：压缩品牌区，导航使用可读菜单；不让导航覆盖内容或主按钮。
- 每个页面只设置一个珊瑚橙主操作，次要操作使用描边或文字按钮。

### 4.2 活动与推荐页面

- 桌面：地图/候选内容作为主区域，成员和投票状态作为辅助区域；必要时采用两栏。
- 手机：按“活动状态 → 推荐类型 → 地图 → 候选详情 → 投票状态”的顺序单栏排列。
- 地图详情在桌面作为浮层，在手机作为不遮挡关键操作的底部或文档流面板。
- 候选地点卡片使用白色表面、16px 圆角、暖灰边框和极淡阴影。

### 4.3 表单与弹窗

- 标签始终可见，不以占位符代替字段说明。
- 输入框与按钮至少 44px 高；错误信息紧邻对应字段。
- 手机弹窗使用接近全宽的单栏布局，键盘弹出后仍能看到当前字段和提交按钮。

### 4.4 状态与反馈

- 加载：说明正在进行的动作，例如“正在比较大家的路线”。
- 无结果：解释可能原因并提供修改需求或重试入口。
- 超时：保留当前填写内容，允许重试。
- 配额不足：说明地图服务暂不可用，不归咎用户。
- 路线不可用：指出受影响的成员或交通方式，并建议调整。
- 未知费用：明确显示“暂不可用”，不显示 0 元或估算值。

## 5. 响应式规则

- `> 1200px`：宽屏双栏，地图和候选信息充分展开。
- `901–1200px`：缩小辅助栏和间距，保持主要流程不变。
- `701–900px`：优先单栏或主次上下排列，导航进入紧凑模式。
- `<= 700px`：明确的移动单栏；卡片、表单、地图详情和投票按钮全宽或易触达。
- `~360–390px`：验证标题换行、邀请码、长地点名、地图控件、弹窗和系统文字放大。

不允许仅通过缩小字体解决空间不足。优先使用换行、重排、折叠次要解释和垂直滚动。

## 6. 实现边界

- 主要修改预计集中于 `styles.css`、`layout.css`、`app.js` 和必要的测试文件。
- 先整理全局设计变量，再逐个页面调整，避免一次性无边界重写。
- 保留现有 DOM 和业务函数能复用的部分；只有当可访问性或响应式布局确实需要时才调整标记结构。
- 不引入大型组件库。只有现有原生实现明显无法满足需求时，才提出局部依赖并单独确认。
- 真实地图接入依赖高德 Key、容器初始化和失败降级；Key 不写入仓库。

## 7. 验证方案

### 自动检查

- 运行 `npm test`，记录 PR #15 已存在的基线失败，确保本轮不新增失败。
- 运行语法检查；`scripts/verify-map.js` 缺失属于基线问题，需单独修复或调整脚本后才能完整通过。
- 为修改过的 API 方法、授权定位、错误分类和关键 DOM 状态添加或更新针对性测试。

### 浏览器检查

- 桌面：Chrome/Edge，至少检查约 1440px 和 1024px 宽度。
- 手机：至少检查 390px 与 360px 宽度，并覆盖触控、长文本和软键盘场景。
- 逐项走通创建、加入、填写需求、推荐、投票、结果和导航入口。
- 检查键盘焦点、文字对比、按钮尺寸、模态框滚动、空状态和失败恢复。

## 8. 实施顺序

1. 建立视觉变量与页面外壳，验证桌面和手机基础排版。
2. 改造活动概览、创建/加入弹窗和需求表单。
3. 改造推荐分组、真实地图容器、候选地点和详情层。
4. 改造投票状态、结果确认和导航入口。
5. 对齐 `PUT /requirements`、`/locations/reverse` 和错误分类。
6. 完成跨尺寸验收、自动测试和基线问题记录。

每一步都先在实际网页中同时检查桌面和手机，再进入下一步。
